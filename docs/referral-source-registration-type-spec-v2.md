# 紹介元入力方式の改善・新規/既存登録区分・再診数指標 仕様書 v2

3つのアップロード文書(「紹介元入力方式の改善 仕様書 v1」「新規/既存登録区分・再診数指標 仕様書 v1」「再診数:手動フラグ対応 仕様書 v1」、後者2つは前者と一体で運用される)を統合し、実装のために補った判断をまとめる。

## 1. 紹介元入力方式の改善

v1のまま実装。`Client`に`referralSourceType`(既存患者/スタッフ/その他のenum)・`referralSourceClientId`・`referralSourceStaffId`・`referralSourceNote`を新設し、新規顧客登録・顧客編集の両画面に反映した(既存の`referredById`は`referralSourceClientId`にリネームして統合。同じ自己参照リレーションのため、既存データはマイグレーションでそのまま引き継いだ)。

### 1.1 UI: 既存患者のインクリメンタル検索

**[v2で具体化]** 「氏名でインクリメンタル検索できるオートコンプリート欄」は、JS実装を増やさない方針を踏襲し、`<input list> + <datalist>`(ネイティブHTML、ブラウザ標準のインクリメンタルフィルタ機能を使う)で実装した。各`<option>`の`value`を`"氏名 #顧客ID"`形式にし、送信時にサーバー側で末尾の`#ID`を正規表現で取り出して`referralSourceClientId`とする。一致しない自由入力だった場合は「紹介元なし」として扱う(サイレントに無視。エラーにはしない)。

### 1.2 紹介人数の集計方式(v1 4節の実装方式の確定)

**[v2で確定・ユーザー確認済み]** v1は「紹介元患者の`referral_count`を自動+1する」としていたが、既存の`ChartRecord.referralCount`は来院記録ごとの任意項目(「この来院で紹介してくれた人数」)であり、来院を伴わない新規登録時点でincrementできる顧客単位の累計フィールドではなかった。ユーザー確認の結果、以下の方針で実装した。

- `Client.referralCount`(Int、既定0)を新設。これを「その顧客の紹介人数の正式な合計」とする
- 以下の両方から加算する:
  1. 来院記録フォームで「紹介をしてくれた」にチェックが入った時(`referralGiven=true`)、その来院の顧客自身の`Client.referralCount`に`referralCount`(未入力なら1)を加算
  2. 新規顧客登録で`referralSourceType=既存患者`が選ばれ、紹介元として指定された時、その紹介元顧客の`Client.referralCount`に+1
- 顧客編集画面で紹介元(既存患者)を変更した場合、旧紹介元から-1・新紹介元に+1する(二重カウント防止)
- 既存の`ChartRecord.referralCount`(来院ごとの個別記録)はそのまま残す。役割が異なるため統合しない
- **マイグレーションでの遡及集計**: 新設フィールドが0スタートだと、これまで記録されていた紹介実績が失われるため、マイグレーション内で以下を遡及計算した: (a) 既存の`ChartRecord.referralGiven=true`の合計、(b) 既存の`referredById`(→`referralSourceClientId`)リンクの本数

## 2. 新規/既存登録区分

v1のまま実装。

- `Client.registrationType`(`RegistrationType`enum: `NEW`/`EXISTING`、必須)を新設。新規顧客登録フォームの冒頭に配置(ラジオボタン、既定は「新規」)
- 「新規」選択時は来院回数(これまでの実績)欄を隠す(CSS `peer-checked`によるネイティブの表示切替。値は送信されるが常に0扱いにする)。「既存」選択時のみ入力欄を表示
- **[v2で確定] サーバー側でも0を強制**: フォームの表示切替はJS不要のCSSのみのため、既存→新規の選び直し時に入力済みの値がDOM上に残るケースがある。`createClient`アクション側でも`registrationType=NEW`の場合は`initialVisitCount`を常に0に矯正する
- ダッシュボードの「新規来院数」(`countNewVisits`)を`registrationType=NEW`の顧客のみに限定した。**[v2でスコープを明記]** 他の期間内新規コホート指標(紹介率・初回→2回目移行率)はv1で言及がないため対象外のままとした

### 2.1 既存データの登録区分バックフィル

**[v2で確定]** この機能導入前に登録された顧客には`registrationType`の実績データが存在しないため、マイグレーションで`initialVisitCount > 0 ? EXISTING : NEW`という近似ルールで一括バックフィルした(3節「来院回数の初期値」機能で「既存患者を登録する場合はこれまでの来院回数を入力」という運用がすでに定着していたため、この近似は実態に近いと判断)。

### 2.2 予約CSV取り込みからの自動生成クライアント

**[v2で追加確認事項]** 予約CSV取り込み(`app/actions/reservations-import.ts`)は、予約データに一致する顧客が見つからない場合に最小限の情報で`Client`を自動生成する処理を持つ。これはアプリ上での意図的な「新規顧客登録」操作ではないため、`registrationType=EXISTING`を設定し、新規来院数の集計に混入しないようにした。

## 3. 再診数(離脱後の復帰)

v1(2つの文書を合わせたもの)のまま実装。

### 3.1 カウントロジック

以下いずれかを満たす来院記録を、その来院月の「再診数」として1件カウントする(重複カウントなし)。

```
(A) departureRecordが存在し、confirmedAtより後で初めての来院である場合(離脱記録ごとに1回まで)
OR
(B) その来院のChartRecord.isManualReturnFlagがtrueの場合(手動フラグ対応 v1)
```

`isManualReturnFlag`は`ChartRecord`に追加した(既存の`testimonialObtained`等、他の来院時チェック項目と同じ置き場所に揃えるため。`Visit`ではなく`ChartRecord`)。来院記録フォームにチェックボックスとして追加した(任意、既定OFF)。

### 3.2 ダッシュボード表示

既存の「離脱数」と同じ並びで「再診数(離脱後の復帰)」のスタットカードを追加した。スタッフ別内訳はv1の指示通り今回は実装しない(全体数のみ)。
