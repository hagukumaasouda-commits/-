# 顧客一覧・来院タイムライン・基本情報カード拡張/来院回数初期値・メニュー構造化 仕様書 v2

2つのv1文書(「顧客一覧・来院タイムライン・基本情報カード拡張」「来院回数初期値・メニュー構造化」、後者が前者の1.3節を差し替え)を統合し、実装のために補った判断をまとめる。

## 1. 顧客一覧への顧客番号列追加

v1のまま実装。`/clients`のテーブルに「顧客番号」列を氏名列の直後に追加し、検索(現状は氏名・カナのみ)に`externalCustomerNo`の部分一致も追加する。

**[v2で追加]** 一覧の「来院回数」列も、3節の`initialVisitCount`を含めた値に変更する(顧客詳細ページと表示を揃える)。

## 2. 来院回数の初期値(`initialVisitCount`)

v1(差し替え後)のまま実装。

- `Client.initialVisitCount`(Int、既定0)を新設。新規登録・編集画面の両方から入力・修正可能
- 表示上の「来院回数」= `initialVisitCount` + 実際に作成された`Visit`件数(顧客一覧・顧客詳細ページの両方)

**[v2で確定] `Visit.visitNo`(各来院の「第X回」表示)には触れない**: `visitNo`は「このアプリで記録した来院の中で何回目か」を表す既存の内部番号で、一意制約(`@@unique([clientId, visitNo])`)や離脱判定のクエリが依存している。仕様書は「表示上の来院回数」という集計値のみを`initialVisitCount`込みにする内容で、個々の来院の「第X回」ラベルまでは対象にしていないと解釈し、`visitNo`はこれまで通り1から採番する(=タイムラインの「第1回」は、このアプリで記録した最初の来院を指す。導入前の実来院回数は`initialVisitCount`で別途カウントする)。

## 3. 来院タイムラインの充実

- 一覧行(折りたたみ時)に来院日・担当スタッフ・本日のメニューに加えて**主訴タグ**を表示
- 展開時の詳細に、来院記録フォームの全項目を表示(既存の評価・前回からの変化・お客様の声・次回確認・生活習慣サポート・回復度・口コミ・紹介に加えて、**[v2で追加]** 抜けていた「次回必須」、および5節の新フィールド「本日のメニュー(プラン/物療チェック)」を追加)
- **[v2で確定] ページング**: 直近10件を表示し、それ以前は「もっと見る」で展開する(JS不要、`<details>`で実装)。10件という件数は「実装時に判断」との指示のため、この値を採用

## 4. 基本情報カードへの項目追加

- 既往・家族データを基本情報カードの**上部**に移動して常時表示(現状は下部に補足的に表示されていたものを、施術前に毎回確認すべき情報として目立つ位置に変更)
- `Client.personalData`(個人データ、自由記述)を新設し、同じく基本情報カード上部に表示。顧客編集画面にも追加
- 健康実践状況(直近の来院記録の`healthPracticeNote`)も基本情報カード上部に表示
- **[確認事項の記録・変更なし]** 生活習慣サポート実施状況の一覧は基本情報カードに追加しない(v1の方針通り。タイムラインの最新来院を見れば足りるため)

## 5. 「本日のメニュー」の構造化

### 5.1 データモデル(`ChartRecord`への追加)

| フィールド | 型 | 説明 |
|---|---|---|
| `menuPlan` | `MenuPlan?`(enum) | ベーシックケア / リペアネスプラン / コンディショニングプラン / ウェルネスプラン(`lib/tags.ts`の`TREATMENT_MENU`と対応) |
| `treatmentModalities` | `Json?` | 物療チェック(コアレ10 / コアレ20 / ブースター / セラゼム / 鍼 / 灸)の済/未マップ |

**[v2で確定] 「物療チェック」は生活習慣サポートとは別の新規フィールド**として追加する(ユーザー確認済み)。既存の`lifestyleSupportStatus`(てる1〜Bトレ、20項目)とは無関係で、混同を避けるため独立させた。

**[v2で確定] `menu_display_override`はDBカラムとして持たない**: 来院記録は作成後に編集する機能が無いため(カルテは記録時点で確定)、「一度上書きしたら自動追従を止める」という挙動はフォーム上(ブラウザ内)だけで完結させれば十分で、保存時点では最終的な表示テキスト1本を、既存の`Visit.menu`にそのまま保存する(スキーマ変更・移行対象を増やさないための簡略化)。

### 5.2 自動生成ロジック

```
自動生成テキスト = menuPlanの表示名 + "(" + 選択された主訴タグをカンマ区切り + ")" + "+" + 選択された物療チェック項目をカンマ区切り
```

**[v2で確定] 表記の簡略化はしない**: v1の例(`リペアネスプラン`→表示は`リペアネス神経整体`、`自律神経症状`→表示は`自律神経`)は、プラン名・タグ名を短縮した特別な変換ルールがあることを示唆しているが、変換表が示されていないため、値をそのまま連結する(短縮しない)。手動での微調整が必要な場合は本文中の上書き欄を使う想定。

### 5.3 UI要件

- 来院記録フォームの「本日のメニュー」は自由入力欄をやめ、メニュープラン選択・主訴タグ・物療チェックのライブプレビューに置き換える(この部分のみクライアントコンポーネント化。フォーム自体・送信方式は変更なし)
- 上書き欄に入力があれば、以降はそちらを優先してプレビューに表示し、保存時もその内容が`Visit.menu`に入る
- **主訴タグの選択欄は、この「本日のメニュー」ブロックの中に移設する**(既存の「主訴タグ」フィールドと同じ`chiefComplaintTags`を使うため、二重管理を避けて1箇所にまとめる)

### 5.4 集計への影響

月次集計(物療・物販、既存機能)は現状`ChartRecord`の実データを直接参照していないため、今回の変更で既存の集計に影響は無い。将来、物療の実施件数などを集計する際に`treatmentModalities`を参照する想定。
