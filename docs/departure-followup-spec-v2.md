# 離脱フォローアップ・担当変更機能 仕様書 v2

はぐくまCRM「気づきチェック」機能の一部として実装する、離脱検知・フォローアップ管理・担当変更提案の仕様。

v1からの変更点は文中に **[v2で変更]** として明示する。全体の変更理由: 既存コードベース(`prisma/schema.prisma` / `lib/reports.ts` / `app/actions/visits.ts`)とのレビューにより、命名規則・既存機能との統合方法・未定義だった運用ルールを確定した。

## 1. 背景・目的

- 患者の離脱を早期に検知し、放置せず追いかける仕組みを作る
- 離脱の兆候(担当スタッフとの関係性含む)が出た時点で、離脱前に手を打てる仕組みを作る
- フォロー漏れ・記録漏れを防ぎ、院長がスタッフ間の相談のきっかけを作れるようにする

## 2. データモデル

**[v2で変更] 命名規則**: 既存の`schema.prisma`は全モデルでPascalCaseのモデル名 + camelCaseのフィールド名を使っている(例: `Staff.passwordHash`, `Client.primaryStaffId`, `AwarenessCheck.checkType`)。v1はsnake_caseで書かれていたため、本バージョンで全面的にcamelCase/PascalCaseに修正した。

### 2.1 カルテ拡張項目(`ChartRecord`への追加)

| フィールド名 | 型 | 説明 |
|---|---|---|
| `requiredVisitInterval` | `VisitInterval?`(enum) | 必要来院ペース。来院のたびに更新可能(初診時だけでなく毎回見直す想定) |

**[v2で変更] enum化**: v1では「選択式」とだけ書かれていたが、既存コードは`ReservationSource`/`ReservationStatus`等と同様enumを多用しているため、以下のenumとして定義する。

**[v3で上書き] 選択肢を8段階に更新**(仕様書「必要来院ペース確定・回復度/口コミ/紹介欄 仕様書 v1」により、既存の顧客管理シートの実際の選択肢と完全一致させたもの。旧5段階から置き換え)。

```prisma
enum VisitInterval {
  TWICE_OR_THRICE_WEEKLY // 週2,3回 = 3日
  WEEK1                  // 1週間 = 7日
  DAY10                  // 10日 = 10日
  WEEK2                  // 2週間 = 14日
  WEEK3                  // 3週間 = 21日
  WEEK4                  // 4週間 = 28日
  MONTH2                 // 2か月 = 60日
  MONTH3                 // 3か月 = 90日
}
```

離脱検知ロジック自体(経過日数 > 必要来院ペースの日数 × 3)に変更はない。選択肢と日数換算のみ差し替え。旧enum値からの対応は以下の通り(既存データがある場合の移行用。旧`MONTHLY`(30日)だけ新選択肢に完全一致するものが無いため、最も近い`WEEK4`(28日)に寄せている):

| 旧 | 新 |
|---|---|
| `WEEKLY`(7日) | `WEEK1`(7日) |
| `BIWEEKLY`(14日) | `WEEK2`(14日) |
| `TRIWEEKLY`(21日) | `WEEK3`(21日) |
| `MONTHLY`(30日) | `WEEK4`(28日、近似) |
| `MAINTENANCE`(60日) | `MONTH2`(60日) |

日数への変換テーブルはコード側(`lib/reports.ts`)の定数として持つ。

判定にはその患者に対して直近の`Visit`に紐づく`ChartRecord.requiredVisitInterval`を使う(履歴は`ChartRecord`が来院ごとに保持しているため、最新値のみ計算に使用すれば良い)。

**[v2で追加] フォールバック規則**: `requiredVisitInterval`が一度も記録されていない患者(過去データ・サロンボードCSV取り込み客など)については、既存の固定閾値と同じ **42日(6週間)** を暫定値として使う。

### 2.2 離脱候補リスト(自動生成・保存不要、都度計算)

検知ロジック:

```
離脱候補 = 最終来院日からの経過日数 > (直近の requiredVisitInterval の日数 × 3)
(requiredVisitInterval 未記録の場合は 42日 を使う)
```

例: 必要来院ペースが「月1回」(30日)の患者 → 90日来院がなければ離脱候補として一覧に表示。

この一覧はダッシュボードまたは専用ページに表示し、スタッフ・院長が確認できるようにする。

**[v2で確定] 既存指標との統合範囲**: 既存の`lib/reports.ts`の`getChurnedClientIds()`(ダッシュボードの「離脱数(6週間以上・予約なし)」指標が参照)を、この個別ペース基準の計算に置き換える。`getChurnedClientIds()`は`getPrepaidDrainWithoutVisit()`(プリカ残高消化ペース検出)からも呼ばれているため、**両方とも**この新しい個別ペース基準に統一する(`getChurnedClientIds`を直すだけで両方に反映される)。

### 2.3 離脱記録テーブル(`DepartureRecord`)

| フィールド名 | 型 | 説明 |
|---|---|---|
| `id` | ID | |
| `clientId` | 参照 | 顧客ID |
| `confirmedBy` | 参照 | 記録したスタッフ |
| `confirmedAt` | 日付 | 離脱を確定・記入した日(フォロースケジュールの起点日) |
| `reason` | 選択式 | 離脱理由(下記プルダウン) |
| `reasonNote` | テキスト(任意) | 「その他」選択時の自由記述、補足メモ |
| `triggeredByCancellation` | 真偽値 | キャンセル後未予約がきっかけの場合はtrue(2.5参照) |

離脱理由プルダウン:
1. 症状改善による卒業(満足)
2. お試し利用(元々継続意思なし)
3. 遠方からの一時利用(帰省・出張等)
4. 砥部店(他店舗)へ変更
5. 効果を実感できなかった
6. 体調・環境の変化(妊娠・出産・病気・怪我等)
7. こちら側のマインド不足
8. その他(自由記述)

※「スタッフとの相性」は理由リストに含めない。関係性の問題は離脱前に2.6の担当変更提案で拾う設計とする。
※「他院へ変更」「経済的理由」「通いにくさ」「転居・引っ越し」「連絡がつかない」は意図的に不採用(満足度が高ければ継続されるという考え方、および「連絡がつかない」は2.4の反応記録と重複するため)。

**[v2で確定] `Client.isActive`との連携**: `Client.isActive`は既存スキーマに「離脱バッチが更新するフラグ」というコメント付きで存在するが、現状は`app/actions/visits.ts`で来院時に`true`にする処理しかなく、`false`にする処理は未実装だった。本機能で実装する:
- `DepartureRecord`作成(離脱確定)時に対象`Client.isActive`を`false`に更新する
- その後、当該クライアントに新しい`Visit`が記録された時点で、既存の`app/actions/visits.ts`の処理により自動的に`isActive: true`へ復帰する(コード変更不要、既存動作のまま)

### 2.4 フォローアップチェックポイント(`FollowupCheckpoint`)

`DepartureRecord`が1件作成されたら、以下5件を自動生成する。

| チェックポイント | 予定日の計算 |
|---|---|
| 3週後 | `confirmedAt` + 21日 |
| 6週後 | `confirmedAt` + 42日 |
| 3ヶ月後 | `confirmedAt` + 90日 |
| 6ヶ月後 | `confirmedAt` + 180日 |
| 1年後 | `confirmedAt` + 365日 |

各チェックポイントのフィールド:

| フィールド名 | 型 | 説明 |
|---|---|---|
| `id` | ID | |
| `departureRecordId` | 参照 | 紐づく離脱記録 |
| `scheduledDate` | 日付 | 対応予定日 |
| `status` | 状態 | 未対応 / 連絡済み |
| `contactMethod` | 選択式 | LINE / 電話 / 手紙・はがき / 対面(来店時) / その他 |
| `response` | 選択式 | 反応あり(継続の意思) / 反応あり(継続なし) / 反応なし / 未実施 |
| `contactedBy` | 参照 | 対応したスタッフ |
| `contactedAt` | 日付 | 実際に対応した日 |
| `note` | テキスト(任意) | 自由記述メモ |

### 2.5 キャンセル後未予約フロー

- 予約キャンセル発生 → 3週間以内に新しい予約が入らない場合、`DepartureRecord`候補として扱う
- `triggeredByCancellation = true`
- `reason`は空欄可(未確定のまま。後から離脱と確定すれば通常通り理由を記入)
- 以降のフォロースケジュール(2.4)は通常の離脱と同じ扱いで進行する
- 一覧・フィルタ上で「離脱」と「キャンセル後未予約」を区別できるよう、`triggeredByCancellation`で表示を分ける

**[v2で確定] 実装方式は(a)都度計算方式を採用**: v1では「自動生成」としか書かれておらず、キャンセルから3週間経過という時間経過をトリガーにする処理が必要になる点が未定義だった。このリポジトリには現状cron/バッチの仕組みが無いため、2.2の離脱候補リストと同じ設計で一貫させ、以下のように実装する:

- `DepartureRecord`は自動では作成しない(DBへの書き込みは発生させない)
- 2.2の離脱候補リストと同じ「都度計算」の一覧に、「予約キャンセル後3週間以内に新規予約が入っていない顧客」も候補として算出・表示する(`Reservation.status = CANCELLED`かつ、そのキャンセル以降に新しい予約が無く、キャンセルから21日以上経過している顧客を抽出するクエリ)
- スタッフがその候補に対して実際に「離脱を記録する」操作をした時点で、`triggeredByCancellation = true`として`DepartureRecord`が作成される(2.3のフローに合流)

### 2.6 担当変更相談(`ReassignmentRequest`)

離脱の手前で、担当スタッフとの関係性に課題がある場合に使う相談機能。

| フィールド名 | 型 | 説明 |
|---|---|---|
| `id` | ID | |
| `clientId` | 参照 | 顧客ID |
| `currentStaffId` | 参照 | 現在の主担当 |
| `initiatedBy` | 選択式 | スタッフ本人 / 院長 / 気づきチェック(自動検知) |
| `requestedByStaffId` | 参照(任意) | 起票したユーザー(気づきチェック起点の場合は空) |
| `note` | テキスト(任意) | 相談メモ |
| `status` | 状態 | 相談中 / 変更確定 / 見送り |
| `newStaffId` | 参照(任意) | 変更確定時の新担当 |
| `handoverNote` | テキスト(任意) | 引き継ぎメモ(何を伝えたか・注意点) |
| `createdAt` | 日付 | |
| `resolvedAt` | 日付(任意) | |

起点は3種類、すべて同じテーブル・同じ相談フローに合流:
1. スタッフ自身が顧客詳細ページの「担当変更を相談する」ボタンを押す
2. 院長が同じボタンから気になる顧客に対して打診する
3. 気づきチェックがパターンを検知し、判定結果の中に提案を表示 → ボタンからそのまま起票

**[v2で確定] 変更確定時の自動反映**: `status`を「変更確定」に更新するのと同時に、システムが自動で以下を行う:
- `Client.primaryStaffId`を`newStaffId`の値に更新する
- `ClientStaff`中間テーブル(複数担当を許容するテーブル)に`newStaffId`のレコードが無ければ追加する

気づきチェックが検知するパターン(初期案。本体設計時に精緻化):
- 来院回数が進んでいる(目安5〜6回目以降)のに、見立て・意味づけの記述に深まりがない、または主訴の改善傾向が見えない(`ChartRecord.evaluation` / `reevaluation` / `meaningConveyed`が該当)
- 「お客様の声」欄(`ChartRecord.clientVoice`)の記述がネガティブ、または継続して空欄
- 同一担当で「こちら側のマインド不足」を理由とした離脱が複数件ある(運用データが蓄積した後)

表示トーンの原則: 責任追及ではなく「一緒に考えるきっかけ」であることが伝わる文言にする。例: 「〇〇さんとの関わり、少し一人で抱え込んでいませんか?」。否定形・評価的な言葉(「対応が悪い」「質が低い」等)は使わない。

## 3. UI要件(初期案)

### 3.1 顧客詳細ページ

- 既存の「AI気づき(関わりの質・離脱兆候)」枠(`app/clients/[id]/page.tsx`の`AwarenessLane`)に、離脱候補判定結果・担当変更提案を表示
- 「離脱を記録する」ボタン(理由プルダウン入力)
- 「担当変更を相談する」ボタン
- フォローアップ履歴タイムライン(過去のチェックポイント対応状況)

### 3.2 フォローアップ管理ページ(新規・一覧)

- 「今週対応すべき人」リスト(チェックポイントの`scheduledDate`が近い順)
- 離脱/キャンセル後未予約のフィルタ
- ワンクリックで連絡方法・反応を記録

### 3.3 気づきチェック結果表示

離脱候補・担当変更提案は、気づきチェック実行結果の一部として表示(本体設計は別途)。
